# 3D data-capture gaps — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the gaps between what the producer can record and what the 3D pane actually receives — a layer that is on by default and never populated, a mode that advertises a view nothing reads, an axis whose units are guessed from disassembly text rather than measured, and half the vector register file that the live producer refuses to read.

**Architecture:** Four independent gaps, in three layers of the stack. Two are one-line honesty fixes in `desktop/` and `cli/` (a start param the GUI never sends; a `mode_visualizations` row that promises a view with no consumer). Two are producer work in `src/dataflow_ptrace.c` and the `df_step` wire shape: recording the SIMD lane width the client currently infers from a mnemonic table, and reading the upper sixteen vector registers through the XSAVE component the current code declines to walk. Nothing here builds a new scene — every consumer already exists and is already drawn.

**Tech Stack:** C11 (`cli/`, `src/`), C++17 + Dear ImGui (`desktop/`), GNU make, Docker lanes.

### Task 3: the lane prism's axis is measured, not inferred from a mnemonic

**Files:**

**Interfaces:**
- Consumes: nothing from other tasks.
- Produces: a new optional `df_step` operand field. **Additive and optional** — a recording without it must still load and must still fall back to `lane_width_for`, because 36 golden recordings and every existing `.asmtrace` on disk lack it.

**G5 — the prism's X axis is a guess.** `lane_width_for` string-matches the disassembly mnemonic (`paddd`→4, `pcmpeqq`→8) against a static table and falls back to 1-byte lanes with a HUD disclaimer. The producer knows better: it decodes the instruction with Capstone to fill the operand in the first place, so the element width is available at the moment of recording and thrown away.

**Design constraints, in order of importance:**

1. **Additive and optional.** Omit the field when the producer cannot determine a width, exactly as it omits other optional fields. `lane_width_recorded` already exists on the consumer side (`standalone.h:321`) to distinguish measured from inferred — keep that distinction and make it mean what it says: **true only when the width came off the wire.**
2. **Do not delete `lane_width_for`.** Every existing recording needs it, and the mnemonic table is the correct fallback. The consumer's rule becomes: recorded width if present, else the guess, else the 1-byte default.
3. **Name it for what it is.** The width of one *element*, not of the operand. `lane_bytes` matches the consumer's own field name.
4. **The golden corpus will move** if the emulator producer emits the field for the corpus routines. That is expected: regenerate per `mk/`'s golden-regen path, then **inspect the diff** — every changed line should differ only by the added field, and any other change is a defect to run down before committing.
