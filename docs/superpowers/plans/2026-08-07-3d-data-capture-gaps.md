# 3D data-capture gaps — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the gaps between what the producer can record and what the 3D pane actually receives — a layer that is on by default and never populated, a mode that advertises a view nothing reads, an axis whose units are guessed from disassembly text rather than measured, and half the vector register file that the live producer refuses to read.

**Architecture:** Four independent gaps, in three layers of the stack. Two are one-line honesty fixes in `desktop/` and `cli/` (a start param the GUI never sends; a `mode_visualizations` row that promises a view with no consumer). One is a client-side honesty fix in `scene3d/` (the lane prism reports a bulk move as a guessed axis). One is producer work in `src/dataflow_ptrace.c`: reading the upper sixteen vector registers through the XSAVE component the current code declines to walk. Nothing here builds a new scene — every consumer already exists and is already drawn.

**Tech Stack:** C11 (`cli/`, `src/`), C++17 + Dear ImGui (`desktop/`), GNU make, Docker lanes.

### Task 3 (REVISED): the prism stops disclaiming a guess it never made

> **This task was re-planned on 2026-08-08 after its premise was refuted at the
> premise check.** The original task said to record the SIMD element width on the
> wire, on the assumption that the producer had it and threw it away. It does not.
> **Capstone 5.0.1 exposes no x86 element width** — probed empirically, not read
> from headers: `paddb`, `paddd`, `paddq` and `addsd` return byte-identical
> operand detail (`size=16`, same access/avx fields). The only discriminator is
> instruction identity, i.e. the very static table the client already has, so
> relocating it to the producer would set `lane_width_recorded` on a value that is
> still inferred — which G5's own constraints forbid. Two knock-on claims fail with
> it: the golden corpus would **not** move (no lane-bearing instruction exists in
> it — the arm64 chain is GPR `add`/`mov`/`ret` and the only wide corpus operand is
> scalar `addsd`), and a `cli_smoke.sh` assertion would be unsatisfiable on an x86
> lane, so it could only self-skip. arm64 *does* carry it (`cs_arm64_op.vas`, exact,
> with `vas == 0` as a built-in omit signal), but `src/dataflow_emu.c:501` shows the
> arm64 guest has `read_wide == NULL`, so it cannot be exercised end to end.
>
> The one path to a genuinely measured x86 axis is **Intel XED**
> (`xed_decoded_inst_operand_element_size_bits()`), already linked in the Pin tier
> at `mk/pintool.mk:109-118`. That is a new decoder dependency in the live capture
> path and needs its own plan; it is not this one.

**Files:**
- Modify: `desktop/src/scene3d/standalone.cpp` (`lane_width_for` and its table; the classification the prism records)
- Modify: `desktop/src/scene3d/standalone.h` (`PrismWrite`'s width fields and their contract)
- Modify: `desktop/src/scene3d/hud.cpp` (the disclaimer that fires today)
- Test: `desktop/test/test_standalone.cpp`

- Produces: a three-way width verdict in place of today's two-way one.

**What the measurement actually showed.** Over `blend_tile` (`cli/scenes_victim.c:82`), the prism draws **12** wide register writes. The table names 4 (`pshufd`×2, `paddd`, `psubd`). Of the 8 it misses:

- **7 genuinely have no element width** — `movdqa`×5, `movaps`, `movd` are bulk moves. There is nothing to know.
- **1 is a real gap** — `punpckldq`, which unambiguously has 4-byte lanes and which neither the table nor Capstone names.

So the defect is not a missing measurement. It is that the prism has **two** states where it needs **three**, and uses the wrong one for the majority case: it draws 1-byte lanes and tells the user it guessed, for instructions whose answer is "this operand has no lanes". That is a false claim in the opposite direction from the one G5 describes, and it fires 7 times out of 12 on the plan's own demo routine.

**The mechanism.** `read_ymm` already reads `NT_X86_XSTATE` and takes YMM upper halves from the fixed offset 576 — that is XSAVE component 2 (`AVX`).
